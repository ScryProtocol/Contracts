# SCP Security Audit — 2026-03-13

## Executive Summary

- **Scope:** Full x402s SCP stack — Solidity contract, hub server, payee server, agent client, storage backends, auth/webhook helpers, CLI tools, chat/music/weather APIs, scp-pay frontend, and all tests (~16,340 lines, 50 files).
- **Method:** Attack-surface-driven audit across 5 parallel threat categories: fund safety, state integrity, auth/access control, input validation, and availability/DoS. Each category was audited independently and findings merged with deduplication.
- **Prior work:** Three audits from 2026-03-07, followed by 7 rounds of fixes. This audit treats the codebase fresh.
- **Overall risk assessment:** The on-chain contract is well-designed with sound balance invariants, signature verification, and reentrancy protection. The primary risks are in the hub's off-chain state machine (storage backend bugs affecting credit accounting, global nonce scoping) and the scp-pay frontend (XSS via innerHTML). Several prior findings remain unfixed or partially fixed.

## Findings

### Critical: MemoryBackend.tx() does not return or await mutator result

- **Location:** `x402s/node/scp-hub/storage.js:51-53`
- **Root cause:** `MemoryBackend.tx()` calls `mutator(this.state)` but neither `await`s the result (async mutators silently fire-and-forget) nor `return`s the mutator's return value. `JsonFileBackend.tx()` correctly returns; `RedisBackend.tx()` correctly awaits but also drops the return value (see H-02).
- **Impact:** Multiple hub code paths read the return value of `store.tx()` for credit balance lookups (server.js:552), channel info (server.js:1256), close credit calculation (server.js:1934), credit balance endpoint (server.js:2100), and withdrawal replay checks (server.js:2141). With MemoryBackend (used in all tests and `:memory:` mode), these return `undefined`, causing credit checks to fail silently, balance reporting to break, and potentially allowing payments without proper credit verification.
- **Reproduction:** Start hub with `:memory:` storage. Issue tickets to accumulate credits. `GET /v1/credit/balance?address=0x...` returns `undefined`.
- **Recommendation:** Fix to `async tx(mutator) { return await mutator(this.state); }`

---

### High: RedisBackend.tx() does not return mutator result

- **Location:** `x402s/node/scp-hub/storage.js:244-265`
- **Root cause:** `RedisBackend.tx()` calls `await mutator(state)` but discards the return value. The returned `result` on line 255 is the Redis MULTI/EXEC result, not the mutator's return value.
- **Impact:** Same as Critical finding — all `store.tx()` call sites that read the return value get `undefined` in production Redis deployments. Credit balance lookups, channel info endpoints, and withdrawal replay checks all affected.
- **Recommendation:** Capture and return: `const mutatorResult = await mutator(state); ... return mutatorResult;`

---

### High: Global nonce maps allow cross-user collision DoS

- **Location:** `x402s/node/scp-hub/server.js:2058-2064` (credit nonces), `server.js:2129-2136` (withdraw nonces)
- **Root cause:** `spentCreditNonces` and `spentWithdrawNonces` are keyed by nonce string alone, not `(signerAddress, nonce)`.
- **Impact:** User A can burn a nonce string and cause user B's valid request with the same nonce to fail. With predictable nonces (timestamps, counters), this is a practical DoS vector.
- **Reproduction:** User A submits credit-pay with `nonce: "abc123"`. User B later submits credit-pay with same nonce. User B is rejected as replay.
- **Recommendation:** Key by `${payerKey}:${cpNonce}` and `${addr}:${nonce}`.

---

### High: Stored XSS via innerHTML in scp-pay frontend

- **Location:** `x402s/scp-pay/index.html:636-638` (credit balance), `:652-666` (channel list), `:696-712` (payment history)
- **Root cause:** `goChannels()` and `goPayments()` build HTML strings from hub API responses and inject via `innerHTML`. Values like balances, addresses, paymentIds, and network labels are interpolated without escaping. A malicious or compromised hub can inject arbitrary HTML/JS.
- **Impact:** Private key theft from localStorage (`x402s.wallet`), payment initiation, session exfiltration. Combined with the unencrypted private key in localStorage, this is a full wallet compromise.
- **Reproduction:** Run a rogue hub returning `paymentId: "<img src=x onerror=alert(document.cookie)>"`. Open scp-pay, view Payments tab. XSS executes.
- **Recommendation:** Create `esc()` helper and wrap all dynamic values, or use `textContent`/DOM APIs instead of innerHTML string concatenation.

---

### High: MemoryBackend tx() atomicity is fragile under async mutators

- **Location:** `x402s/node/scp-hub/storage.js:51-53`
- **Root cause:** `MemoryBackend.tx()` has no locking. Currently safe because all mutators are synchronous (JS event loop guarantees run-to-completion). But adding any `await` inside a mutator silently breaks atomicity with no runtime error.
- **Impact:** Latent — currently safe but brittle. Any future async mutator breaks atomicity silently.
- **Recommendation:** Add assertion: `if (result && typeof result.then === 'function') throw new Error('MemoryBackend.tx() mutator must be synchronous');`

### Medium: Unverified payee channel registration

- **Location:** `x402s/node/scp-hub/server.js:1457-1482`
- **Root cause:** `/v1/hub/register-payee-channel` accepts `body.totalDeposit` from the caller without on-chain verification.
- **Impact:** Payee can register with inflated balance, corrupting hub's internal accounting.
- **Reproduction:** Payee opens channel with 100 USDC, registers with `totalDeposit: "1000000000"`.
- **Recommendation:** Fetch `getChannel(channelId)` on-chain to verify totalBalance.

---

### Medium: Credit withdrawal sends only ETH regardless of channel asset

- **Location:** `x402s/node/scp-hub/server.js:2106-2162`
- **Root cause:** `/v1/credit/withdraw` always sends native ETH via `signer.sendTransaction` with `value`, regardless of whether credits were accumulated from ERC20 payments.
- **Impact:** USDC credits → ETH withdrawal creates massive value mismatch (1 USDC unit = 1 wei ETH).
- **Reproduction:** Accumulate 1000000 USDC credits. Withdraw. Hub sends 1000000 wei ETH (~$0).
- **Recommendation:** Track credit asset type. Transfer correct asset on withdrawal.

---

### Medium: Webhook SSRF via IPv6/DNS rebinding

- **Location:** `x402s/node/scp-hub/webhooks.js:25-41`
- **Root cause:** `isPrivateHost()` only checks IPv4 patterns + `localhost` + `[::1]`. Does not block IPv4-mapped IPv6, IPv6 ULA/link-local, or hostnames resolving to private IPs.
- **Impact:** Admin with valid token can register webhook targeting internal services via `http://[::ffff:127.0.0.1]:8080/`.
- **Recommendation:** Resolve hostname via `dns.lookup()` before checking. Add IPv6 ULA/link-local/mapped ranges.

---

### Medium: Unauthenticated information disclosure on multiple endpoints

- **Location:** `server.js:1164` (`/v1/payments/:id`), `:1268` (`/v1/payee/inbox`), `:1484` (`/v1/payee/channel-state`), `:2096` (`/v1/credit/balance`)
- **Root cause:** These endpoints return payment details, payee ledgers, signed channel state (including `sigA`), and credit balances without authentication.
- **Impact:** `/v1/payee/channel-state` exposes `sigA` (close-authorization credential). Payment history enumerable.
- **Recommendation:** Add payee-auth signature verification. Guard `sigA` exposure.

---

### Medium: Handle route payment verification is weak

- **Location:** `x402s/node/scp-hub/server.js:2174-2188`
- **Root cause:** Handle route checks `paymentId` existence in store but does not verify ticket cryptographic signature. No replay protection — same paymentId reusable unlimited times.
- **Impact:** Anyone knowing a valid paymentId (obtainable from unauthenticated `/v1/payments/:id`) can access handle data without paying. Prior finding partially fixed but insufficient.
- **Recommendation:** Use `verifyTicket()` from `ticket.js`. Track consumed paymentIds.

---

### Medium: Ticket signed before atomic CAS section (CPU DoS)

- **Location:** `x402s/node/scp-hub/server.js:783-793` (signing) vs `:834-956` (atomic tx)
- **Root cause:** Hub signs ticket and channel state before entering `store.tx()` that checks quote existence. Parallel requests for the same quote force O(N) signing operations though only one succeeds.
- **Impact:** CPU amplification — 100 parallel requests = 297 wasted signature operations.
- **Recommendation:** Move CAS check before signing, or add rate limit on issue endpoint.

---

### Medium: Withdrawal nonce burned on tx failure

- **Location:** `x402s/node/scp-hub/server.js:2146-2161`
- **Root cause:** On-chain withdrawal failure re-credits balance but nonce stays spent.
- **Impact:** User must generate new signature. Griefable if hub operator intentionally runs with insufficient ETH.
- **Recommendation:** Allow nonce retry when recorded status is `failed`.

---

### Medium: Hub ABI mismatch — openChannel missing hubFlags

- **Location:** `x402s/node/scp-hub/server.js:81` vs `IX402StateChannel.sol:64-72`
- **Root cause:** Hub ABI has 6 parameters; contract expects 7 (missing `hubFlags`).
- **Impact:** Hub's `openChannel` calls revert at ABI encoding level. Blocks payee channel flow.
- **Recommendation:** Align hub ABI with deployed contract.

---

### Medium: Hub ABI mismatch — rebalance tuple wrong types

- **Location:** `x402s/node/scp-hub/server.js:84` vs `IX402StateChannel.sol:102-107`
- **Root cause:** Hub uses `uint256` for `stateNonce`/`stateExpiry`; contract uses `uint64`. Different ABI encoding.
- **Impact:** Rebalance calls produce wrong function selector. Hub cannot rebalance channels.
- **Recommendation:** Use `uint64` to match Solidity struct.

---

### Medium: Hub ABI mismatch — getChannel missing hubFlags field

- **Location:** `x402s/node/scp-hub/server.js:86` vs `IX402StateChannel.sol:109-112`
- **Root cause:** Hub's getChannel return tuple has 9 fields; contract returns 10 (missing `hubFlags`).
- **Impact:** Garbled decode — wrong `latestNonce`, wrong `isClosing`. Could cause stale nonce issuance or missed closing state.
- **Recommendation:** Add `uint8 hubFlags` to return tuple.

### Medium: postMessage to wildcard origin leaks payment data

- **Location:** `x402s/scp-pay/index.html:1044,1100`
- **Root cause:** `window.parent.postMessage({...}, "*")` after payment. Any iframe parent receives payment details.
- **Impact:** Malicious embedding site captures paymentIds and amounts.
- **Recommendation:** Replace `"*"` with configurable allowed origin.

---

### Medium: postMessage listener lacks origin validation

- **Location:** `x402s/scp-pay/index.html:1118`
- **Root cause:** Accepts `x402:config` messages from any origin, allowing URL injection into payment input.
- **Impact:** Attacker embeds scp-pay in iframe, injects malicious payment URL.
- **Recommendation:** Validate `e.origin` against allowlist.

---

### Medium: No RPC request timeouts

- **Location:** `server.js:649`, `:726`, `:1181`, `:1672`, `:1908`
- **Root cause:** ethers.js v5 JsonRpcProvider has no built-in timeout. Hung RPC keeps HTTP connections open indefinitely.
- **Impact:** Unresponsive RPC → all payment/close requests hang → connection exhaustion → full hub outage.
- **Recommendation:** Set `timeout: 10000` on provider. Add `server.setTimeout(30000)`.

---

### Medium: Webhook retry timers accumulate without bound

- **Location:** `x402s/node/scp-hub/webhooks.js:277-293`
- **Root cause:** Failed deliveries schedule exponential retries with no cap on total pending.
- **Impact:** Failing endpoint + rapid events → hundreds of thousands of pending timers → memory exhaustion.
- **Recommendation:** Cap pending retries per hook (e.g., 100).

---

### Medium: Rate limit map grows without bound

- **Location:** `x402s/node/scp-hub/server.js:411-415`
- **Root cause:** Cleanup runs probabilistically (2% of requests). Diverse IPs accumulate faster than cleanup.
- **Impact:** Memory exhaustion under sustained botnet-style attack.
- **Recommendation:** Add hard cap on `rateWindow.size`.

---

### Medium: Channel lookup endpoint is RPC amplification vector

- **Location:** `x402s/node/scp-hub/server.js:1171-1228`
- **Root cause:** Single request generates 10+ RPC calls (chunked queryFilter + per-channel getChannel + payment scan).
- **Impact:** Exhausts RPC quota, cascading to ticket issuance failures.
- **Recommendation:** Stricter rate limit (10/min), result caching, bounded block scan range.
